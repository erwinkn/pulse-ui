Pulse scheduling runs work in the current render session's task scope, or the
app's when there is no active render. A task scope is a lifetime: closing the
owner cancels and drains everything scheduled in it.

```python
from pulse.tasks import every, later, repeat, spawn
```

For timers, use the helpers directly from `pulse`:

```python
import pulse as ps

ps.later(1.0, do_something)
ps.repeat(5.0, poll_data)
ps.every(5.0, poll_data)
```

## later

Schedule a callback to run once after a delay.

```python
def later(
    delay: float,
    fn: Callable[P, Any],
    *args: P.args,
    **kwargs: P.kwargs,
) -> ps.Task
```

`fn` can be synchronous or asynchronous. If it returns an awaitable, Pulse
waits for it before the scheduled task finishes.

The returned `ps.Task` supports `.cancel()`, `.done()`, `.cancelled()`, and
`await task.wait()`. `wait()` returns a `TaskOutcome` (`COMPLETED`, `CANCELLED`,
or `FAILED`) so you can react to how the task ended. Route unmounting does not
cancel `later()` callbacks; cancel the task when a route-local callback should
not run after unmount.

```python
class NotificationState(ps.State):
    message: str = ""

    def show(self, text: str):
        self.message = text
        ps.later(3.0, self.clear)

    def clear(self):
        self.message = ""
```

## repeat and every

Run a callback repeatedly at a fixed interval.

```python
def repeat(interval: float, fn: Callable[P, Any], ...) -> ps.Task
def every(interval: float, fn: Callable[P, Any], ...) -> ps.Task
```

`repeat` waits one interval before the first run. `every` runs `fn` once
immediately, then every interval. Neither reserves an argument name, so
`*args`/`**kwargs` always reach `fn`.

For async callbacks, the next interval starts after the callback completes, so
executions do not overlap. Callback exceptions are reported through the event
loop's exception handler, and the loop continues.

```python
class LiveDataState(ps.State):
    data: dict = {}

    def start_polling(self):
        self.handle = ps.repeat(5.0, self.fetch_data)

    def stop_polling(self):
        self.handle.cancel()

    async def fetch_data(self):
        self.data = await api.get_latest()
```

## spawn

Run a coroutine in the active task scope.

```python
def spawn(
    coroutine: Coroutine[Any, Any, Any],
    *,
    name: str | None = None,
) -> ps.Task
```

The coroutine's exceptions are reported through the event loop's exception
handler with the task name. Cancellation propagates normally.

```python
from pulse.tasks import spawn

class BackgroundWorkState(ps.State):
    status: str = "idle"

    def start_work(self):
        self.status = "running"
        spawn(self._do_work(), name="background-work")

    async def _do_work(self):
        await asyncio.sleep(5)
        self.status = "done"
```

`TaskScope` is the internal lifetime these helpers resolve to. Reach for it
directly only when you own a scope:

```python
from pulse.tasks import TaskScope

async with TaskScope("worker") as scope:
    scope.spawn(work(), name="worker-task")
```

## Automatic cleanup

Scheduling helpers use the current render session's task scope when called
during a render and the app's otherwise. When the owner closes or shuts down:

- Pending `later` callbacks are cancelled.
- `repeat`/`every` loops are stopped.
- Spawned coroutines are cancelled and drained.

## Event loop

A task scope binds to the event loop where `await scope.start()` runs.
`App.task_scope` starts in the FastAPI lifespan, and a render session's scope
starts in `App.create_render`. Handle-returning scheduling from another thread
or event loop, before `start()`, or after `close()` raises `RuntimeError`
rather than queueing work that could never run.

Scheduling is therefore loop-affine: `spawn`, `later`, `repeat`, and `every`
must be called from the loop that owns the scope. Threads are handled inside
the reactive runtime, which posts work back onto the serving loop when a
synchronous FastAPI endpoint writes state from Starlette's threadpool. That
bridge is not part of the public scheduling API.

## Untracking

Scheduled callbacks run with an untracked reactive context, so reading a
signal inside a timer does not create a reactive dependency:

```python
class State(ps.State):
    count: int = 0

    @ps.effect
    def setup_timer(self):
        ps.later(1.0, lambda: print(f"Count is {self.count}"))
```
